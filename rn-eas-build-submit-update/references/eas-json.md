# `eas.json` — 3 profiles

Canonical shape. Place at project root. Generated by `eas build:configure` on first run; then maintain by hand.

```json
{
  "cli": {
    "version": ">= 21.0.0",
    "appVersionSource": "remote"
  },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal",
      "ios": {
        "simulator": true
      },
      "channel": "development"
    },
    "preview": {
      "distribution": "internal",
      "ios": {
        "simulator": false
      },
      "android": {
        "buildType": "apk"
      },
      "channel": "preview"
    },
    "production": {
      "autoIncrement": true,
      "channel": "production"
    }
  },
  "submit": {
    "production": {
      "ios": {
        "appleId": "you@example.com",
        "ascAppId": "1234567890",
        "appleTeamId": "ABCDE12345"
      },
      "android": {
        "serviceAccountKeyPath": "./google-play-service-account.json",
        "track": "internal"
      }
    }
  }
}
```

`cli.version` is just a floor — it only needs to be a lower bound the installed `eas-cli` satisfies (check the actual installed/latest version with `npm view eas-cli version`; example above reflects a recent major, not a hard requirement).

⚠️ **Do not pin `ios.image`.** Since 2026-04-28 App Store Connect refuses uploads not built with **Xcode 26 + the iOS 26 SDK**. Omitting `image` (or setting `"image": "auto"`) resolves to `macos-tahoe-26.5-xcode-26.6` on SDK 57 and satisfies this; an inherited pin to an older image builds fine and then fails at `eas submit`. See `rn-publishing-payments/references/review-guidelines.md`.

## Profile semantics

### `development`
- For day-to-day dev with Expo Dev Client.
- iOS: simulator build (no provisioning profile needed).
- Android: APK (sideload-able).
- Distribution: internal (you + your team, via Expo Go-like install link).
- Use: install on your dev devices, run `npx expo start --dev-client`.

### `preview`
- For QA + stakeholder review on real devices.
- iOS: device build (for TestFlight or ad-hoc internal distribution).
- Android: APK on internal track or sideload.
- Channel: `preview` → EAS Updates pushed to this channel reach this build, not production users.
- Use: run final smoke test before promoting.

### `production`
- For the store.
- `autoIncrement: true` — bumps `ios.buildNumber` and `android.versionCode` automatically on every build. You ALWAYS bump `version` (the marketing version) manually in `app.json` before kicking a production build.
- Channel: `production` → end-user devices.

## Commands

```bash
# Day-to-day
eas build --profile development --platform ios
eas build --profile development --platform android

# Pre-release smoke
eas build --profile preview --platform all

# Release
eas build --profile production --platform all
eas submit --profile production --platform ios     # or --platform android, or --platform all
```

## `cli.appVersionSource: "remote"`

Means EAS owns the build number — it's stored on the EAS server and incremented per build. The alternative `"local"` reads from `app.json` and bumps on commit. `remote` is the modern default — single source of truth, no merge conflicts on `app.json` from parallel builds.

## Submit credentials (App Store + Play Store)

- **iOS**: `appleId` + `ascAppId` (App Store Connect) + `appleTeamId`. EAS will use the stored APNs/cert credentials.
- **Android**: a Google Play service account JSON. Generate in Google Cloud Console → IAM → Service Accounts → grant "Release Manager" in Play Console. Path to JSON goes in `serviceAccountKeyPath`. NEVER commit this JSON — add to `.gitignore`.
